# 中间路由平台 V0.1 产品与实施计划（待评审）

> ⚠️ **HISTORICAL**：已被《Midroute 自主中间路由平台 PRD》(tasks/prd-midroute-independent-platform.md, 2026-09-04) 取代，仅存档，不再作为实施依据。


> 状态：Draft / 暂不进入大规模开发  
> 日期：2026-09-02  
> 定位：本地优先的 AI 凭据、套餐、用量监控与请求路由平台

## 1. 一句话定义

把不同 AI 平台的 API Key、组织账号和 Coding Plan 连接到一个本地网关，统一查看可用模型、套餐与限额、Token/费用、实时健康度，并按规则选择合适的模型与凭据。

## 2. 先说结论：哪些能做，哪些不能假设

| 能力 | 可行性 | V0.1 方案 |
|---|---:|---|
| 验证 API Key 属于哪家平台 | 高 | 用户显式选择 Provider，再调用官方账号或模型接口校验；不对密钥做猜测式扫描 |
| 查看该凭据可用模型 | 高 | 优先使用官方模型端点，再叠加本地模型目录与实测可用性 |
| 统计经过本地网关的 Token、请求量和费用 | 高 | 从真实响应用量与请求日志聚合；缺少用量时明确标为估算 |
| 查看绕过本地网关的全账号用量 | 中 | 仅当 Provider 提供官方 Usage/Cost API 且凭据权限足够时支持 |
| 查看 API 额度和限流 | 中 | 联合官方额度 API、限流响应头、计费设置和本地观测值 |
| 读取 Coding Plan 的 5 小时/每周限额 | 中低，因平台而异 | 只做有官方或稳定本地 Runtime 接口的适配器；不窃取浏览器 Cookie，不依赖页面爬虫 |
| 监测模型是否拥挤 | 可推断，难以官方确证 | 展示健康、繁忙、拥堵、不可用的本地推断与置信度，综合 TTFT、延迟、429、5xx、超时和官方状态 |

### 核心原则

1. 不把 API Key、Coding Plan、OAuth 会话混成一种凭据。
2. 不承诺所有平台都能读取剩余额度。
3. 每个数值都带来源、采集时间和可信度。
4. 密钥不进前端、不进日志、不在数据库中明文保存。
5. 每次路由都能解释选中了哪个平台、模型和凭据，以及选择原因。

## 3. 产品边界

### 3.1 V0.1 必须完成

- 本地添加、编辑、禁用和删除 Provider 连接。
- 支持三类连接：API Key、管理凭据、Runtime 会话。
- 列出每个连接的平台、账号或项目、可用模型、权限与能力。
- 对外提供 OpenAI-compatible 本地网关，业务工具只配置一个 Base URL 和一个本地访问 Token。
- 记录经过网关的模型、请求数、输入/输出/缓存 Token、延迟、状态码和估算费用。
- 根据 Provider 能力同步套餐、账单、额度、限流和重置时间。
- 提供手动刷新、定时刷新、异常重试和采集状态。
- 按成本、健康度、优先级和剩余额度进行基础路由与故障切换。

### 3.2 首版不做

- 不做多租户 SaaS、团队计费和商业支付。
- 不保存请求 Prompt 和模型完整回答；默认只记录元数据。
- 不通过爬取网页或注入脚本绕过平台限制。
- 不允许 Coding Plan 凭据被当作普通 API Key 转卖或共享。
- 不在 V0.1 实现语义路由、A/B 模型评测和跨区域部署。

## 4. 核心用户故事

### US-001：统一管理凭据

作为个人开发者，我希望一处管理多家 API Key 和 Coding Plan 连接，但不暴露原始密钥。

验收条件：

- [ ] 每个连接显示 Provider、连接类型、别名、状态和最近校验时间。
- [ ] UI 不能再次显示完整凭据，日志搜索不能找到原始凭据。
- [ ] 密钥保存在操作系统密钥库或经主密钥加密的本地 Vault。
- [ ] 禁用连接后，新请求不再选中该凭据。

### US-002：识别可用模型与能力

作为个人开发者，我希望看到每个连接真正可用的模型，以便正确路由。

验收条件：

- [ ] 模型列表显示官方 ID、统一别名、上下文上限、输入类型和价格版本日期。
- [ ] “官方列出”和“已实测可用”是两个独立状态。
- [ ] 无权限的模型不参与自动路由。

### US-003：查看用量和额度

作为个人开发者，我希望一眼看到每家平台的 Token、费用、剩余额度和重置时间。

验收条件：

- [ ] 支持 5 小时、日、周、月和自定义时间窗口。
- [ ] 每个数值显示来源：官方 API、路由观测、本地 Runtime 或用户配置。
- [ ] 每个数值显示最后刷新时间，以及 exact、reported、estimated、unavailable 可信度。
- [ ] 无法取得的数据显示“平台未提供”，不显示为 0。

### US-004：监测拥挤度和健康状态

作为个人开发者，我希望知道当前哪个模型更稳定，以便避开拥堵。

验收条件：

- [ ] 每个 Provider + Model 显示健康度、置信度、样本数和最后采样时间。
- [ ] 展示 TTFT P50/P95、总延迟 P50/P95、429 率、5xx 率和超时率。
- [ ] 不把用户自己的额度用尽误判为全平台拥堵。
- [ ] 健康度下降时可以触发路由降权，但手动锁定规则优先。

### US-005：统一路由与故障切换

作为个人开发者，我希望工具只连接一个地址，网关自动选择凭据和模型。

验收条件：

- [ ] 兼容核心 OpenAI Chat/Responses 请求和流式输出。
- [ ] 支持逻辑模型别名，例如 coding-fast 映射到候选模型集合。
- [ ] 支持固定、优先级、最低成本、最佳健康度和额度保护策略。
- [ ] 只在可安全重试的错误上切换，避免非幂等请求重复执行。
- [ ] 路由决策日志不含 Prompt、回答和原始凭据。

## 5. 推荐产品形态

V0.1 推荐做成“本地常驻网关 + Web 管理台”，不先做云端 SaaS。

~~~mermaid
flowchart LR
  A[IDE / CLI / App] -->|OpenAI-compatible API| G[Local Gateway]
  G --> R[Routing Engine]
  R --> P1[OpenAI Adapter]
  R --> P2[Anthropic Adapter]
  R --> P3[Gemini Adapter]
  R --> P4[Coding Runtime Adapter]
  G --> O[Usage & Health Collector]
  O --> D[(Local SQLite)]
  C[Web Console] --> G
  V[OS Keychain / Encrypted Vault] --> G
  S[Official Status & Usage APIs] --> O
~~~

### 技术选型建议

- 前端：React + TypeScript + Vite。
- 后端：Node.js + TypeScript，首版用 Fastify 或 Hono。
- 数据库：SQLite，时序统计先用分钟/小时聚合桶，不立即引入 Prometheus 或 ClickHouse。
- 密钥：macOS Keychain 优先；跨平台时接入各系统密钥库。SQLite 只保存 credential reference。
- 定时任务：进程内 scheduler + 持久化 job state，首版不引入 Redis。
- 运行形态：先提供 localhost 服务和管理页，稳定后再用 Electron 或 Tauri 封装。

## 6. 系统分层

### 6.1 Connector Registry

每个 Provider 适配器显式声明是否支持以下能力：

- verifyCredential
- listModels
- fetchUsage
- fetchCost
- fetchQuota
- fetchPlanWindows
- fetchOfficialStatus
- probeModel
- proxyRequest

不支持的能力返回 unsupported，不用空数组或 0 伪装成功。

### 6.2 Credential Vault

- 数据库只保存连接信息、密钥库引用和脱敏指纹。
- 原始凭据仅在调用时短暂进入后端内存。
- 日志结构化输出前统一做 secret redaction。
- 备份默认不含密钥；导出密钥需要二次确认和独立加密。

### 6.3 Model Catalog

统一记录 Provider model ID、显示名、上下文长度、输入/输出类型、tool use、structured output、reasoning、单价、价格生效日期、可用性和最近实测时间。

### 6.4 Usage & Quota Collector

数据来源优先级：

1. Provider 官方 Usage/Cost/Quota API。
2. 经过本地网关的真实响应 usage 与 rate-limit headers。
3. 官方 CLI/Runtime 返回的结构化用量事件。
4. 根据 tokenizer 与定价表得到的估算值。
5. 用户手动录入的套餐窗口和阈值。

同一指标不盲目求和，而是保留来源并展示对账差异。

### 6.5 Health & Congestion Engine

“拥挤度”在产品中建议命名为“实测健康度”，因为 Provider 通常不公开模型实时排队长度。

计算输入：

- 首 Token 时间 TTFT P50/P95。
- 总请求时间 P50/P95。
- 429、529/503/5xx、超时和连接断开比率。
- 官方 Status 事件。
- 本账号剩余额度和限流窗口。

故障分类：

- account_limited：当前凭据或账号自身无额度。
- provider_degraded：多凭据、多地区或官方状态均出现异常。
- model_busy_inferred：特定模型延迟和错误显著偏高，但没有官方确认。
- network_issue：本机 DNS、代理、TLS 或网络问题。

首版使用可配置规则、置信度、滞回和熔断窗口，不做黑盒机器学习；样本不足时不自动切换。

### 6.6 Routing Engine

路由输入包括逻辑模型名、功能要求、成本上限、延迟偏好、健康度、剩余额度、用户优先级和数据区域。

路由输出包括选中的 Provider、Model、Credential、规则 ID、候选排名和可解释原因。

故障切换规则：

- 连接超时、429 和部分 5xx 可进入候选切换。
- 鉴权失败立即隔离凭据，不向其他 Provider 泄露原请求。
- 流式响应已经输出内容后，默认不在后台重放整个请求。
- Tool call、代码执行、文件写入等非幂等任务禁止自动重放。

## 8. 本地 API 草案

管理 API：

- POST /api/connections
- POST /api/connections/:id/verify
- POST /api/connections/:id/refresh
- GET /api/connections/:id/capabilities
- GET /api/models
- GET /api/usage?window=5h|day|week|month
- GET /api/quotas
- GET /api/health
- GET/POST /api/routing-policies
- GET /api/routing-decisions/:requestId

网关 API：

- POST /v1/chat/completions
- POST /v1/responses
- GET /v1/models

本地网关自身使用独立访问 Token，并默认只监听 127.0.0.1。

## 9. 首批适配器与验证顺序

### A 级：V0.1 正式支持

1. OpenAI API：模型发现、路由、本地 usage、组织 Usage/Cost（需要管理凭据）。
2. Anthropic API：模型配置、路由、本地 usage、组织 Usage/Cost（需要 Admin API 凭据）。
3. Gemini API：模型与路由、本地 usage；项目用量、额度和账单需要 Google Cloud Monitoring/Quota/Billing 权限。

### B 级：M0 可行性试验，不先承诺

1. Codex Coding Plan：优先使用官方本地 Runtime 或产品提供的用量能力；不导出登录 Token，不将会话伪装为 OpenAI API Key。
2. Claude Code Plan：只读取官方 CLI/Runtime 明确暴露的模型、用量和重置信息；不解析网页私有接口。

如果 M0 证明个人套餐没有稳定接口，按以下方式降级：

- 只显示登录状态和可用模型。
- 读取 Runtime 返回的“剩余/重置时间”结构化事件。
- 允许用户手动设定套餐窗口，再用本地观测估算，并明确显示 estimated。

## 10. 安全与隐私基线

- 威胁模型至少覆盖本地恶意进程、日志泄密、数据库备份泄密、SSRF、恶意 Base URL、前端 XSS 窃密钥和插件供应链。
- 凭据展示一律脱敏；错误对象写日志前过滤 header、URL query 和 body 中的 secret。
- Provider Base URL 默认仅允许 HTTPS；自定义端点需显式开启，并阻止访问云元数据和本机敏感端口。
- 管理台与网关 API 使用不同的本地令牌。
- 默认不记录 Prompt/回答；临时调试必须按单次请求开启并设置自动删除时间。
- 适配器只能获取自身的 credential handle，不能枚举其他密钥。

## 11. 实施里程碑

### M0：可行性与协议冻结（3–5 天）

产出：能力矩阵、三个 API Provider 读取试验、两个 Coding Plan 安全读取试验、统一适配器接口、数据模型决策记录。

验收：

- [ ] 每项 Provider 能力被标为 official、runtime、observed、estimated 或 unsupported。
- [ ] 用测试凭据完成校验，任何输出均不含凭据。
- [ ] 明确 Codex/Claude Code 能否稳定取得 5 小时/周限额，不能取得时写入产品限制。
- [ ] 冻结 Adapter Contract v1，评审后才进入 M1。

### M1：安全连接与模型目录（5–7 天）

产出：项目骨架、SQLite migration、Credential Vault、连接管理 UI、OpenAI/Anthropic/Gemini 适配器。

验收：

- [ ] 添加、校验、禁用、删除连接完整可用。
- [ ] 重启后连接存在，原始密钥不在 SQLite 明文中。
- [ ] 模型目录区分官方列出和实测状态。
- [ ] 自动化测试覆盖日志脱敏和适配器错误规范化。

### M2：网关与本地用量计量（7–10 天）

产出：OpenAI-compatible gateway、流式转发、usage event、价格版本、时间窗口聚合。

验收：

- [ ] 非流式和流式请求都能正确透传。
- [ ] Provider 响应提供的 Token 标为 exact。
- [ ] 重试不被错误统计成多个用户请求，同时保留 Provider 实际成本。
- [ ] 仪表盘可查看 5h、日、周、月的请求、Token 和费用。

### M3：套餐、额度与对账（5–8 天）

产出：Usage/Cost/Quota 同步任务、限额窗口模型、对账页、数据可信度。

验收：

- [ ] 有管理权限时取得官方用量，无权限时返回可理解的限制说明。
- [ ] 官方用量与本地观测分列展示差异。
- [ ] 刷新任务支持手动、定时、退避和最近成功时间。
- [ ] 滚动窗口、固定账单窗口和跨时区计算有单元测试。

### M4：健康度、路由与故障切换（7–10 天）

产出：健康探测、评分引擎、路由策略、熔断、故障切换、决策解释。

验收：

- [ ] 账号额度、Provider 故障和本地网络错误能被区分。
- [ ] 小样本不触发自动路由变化。
- [ ] 关闭故障切换时，请求始终使用锁定目标。
- [ ] 可以用 request ID 回放每次路由决策。
- [ ] 流式中断不自动重放已输出内容的请求。

### M5：告警、备份与桌面化（5–8 天）

产出：看板优化、阈值告警、数据导出/备份、桌面封装、升级与崩溃恢复策略。

验收：

- [ ] 额度达到 70%/90%、凭据失效、模型持续降级时可告警。
- [ ] 导出的运行数据不含密钥和 Prompt。
- [ ] 应用升级不覆盖用户数据，数据库 migration 可恢复。
- [ ] 完成真实桌面包的启动、网关请求、重启和密钥读取 smoke test。

粗略总工期：单人全职约 5–8 周。M0 结束后再根据 Coding Plan 的真实接口能力修正。

## 12. 功能需求清单

- FR-1：系统必须支持显式选择 Provider 后添加凭据。
- FR-2：系统必须在服务端校验凭据，前端不得直连 Provider。
- FR-3：系统必须为每个连接生成能力矩阵。
- FR-4：系统必须保留 Provider 原始模型 ID。
- FR-5：系统必须支持逻辑模型别名。
- FR-6：系统必须为用量数值记录来源与可信度。
- FR-7：系统必须区分未知、0 和不支持。
- FR-8：系统必须支持 5 小时、日、周和月窗口。
- FR-9：系统必须支持滚动窗口和固定账单窗口。
- FR-10：系统必须支持手动刷新。
- FR-11：系统必须对同步失败进行指数退避。
- FR-12：系统必须限制主动健康探测的频率和成本。
- FR-13：系统必须将健康状态与置信度一起返回。
- FR-14：系统必须在路由前排除禁用、无权限或已用尽额度的连接。
- FR-15：系统必须记录不含内容的路由决策。
- FR-16：系统必须默认只监听 localhost。
- FR-17：系统必须在日志写入前完成密钥脱敏。
- FR-18：系统必须将 Prompt/回答持久化设置为默认关闭。

## 13. 成功指标

- 添加一个 API Provider 连接在 2 分钟内完成。
- 经过网关请求的 Token 统计覆盖率不低于 99%，估算值不冒充精确值。
- Provider 返回 usage 时，本地聚合与原始事件差异为 0。
- 健康度下降后，新请求在一个采样窗口内避开已熔断目标。
- 所有故障切换都能用 request ID 解释。
- 密钥扫描、日志扫描和导出文件扫描均不发现原始凭据。

## 14. 主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 个人 Coding Plan 无公开用量 API | 无法统一读取 5h/周限额 | M0 先验证；无稳定接口就标记 unsupported 或 estimated |
| 网页私有接口变化 | 连接频繁失效 | 不以页面爬虫为核心方案 |
| 拥挤度误判 | 路由抖动或费用升高 | 分开账号、平台、网络故障，增加置信度、滞回和熔断窗口 |
| 主动探测消耗额度 | 监控本身引起成本 | 优先用真实流量，主动探测设置预算和最低间隔 |
| 价格或模型规格变化 | 历史费用重算错误 | 价格与模型元数据版本化，历史事件绑定当时版本 |
| 凭据集中存储 | 单点泄密影响大 | OS Keychain、最小权限、日志脱敏、适配器隔离、安全导出 |
| 兼容接口语义差异 | Tool call/流式细节丢失 | 定义内部规范化事件，按 Provider 做 contract tests |

## 17. 当前官方能力依据

- OpenAI Usage API 可按时间桶、项目、API Key 和模型查询用量，Cost 端点用于账单对账；这类端点需要组织级管理权限。
- Anthropic 提供组织级 Usage and Cost API，需要 Admin API Key 或具备管理范围的 OAuth 凭据；普通个人账号与企业/组织能力不能混为一谈。
- Gemini 限额以项目为单位，包括 RPM、TPM、RPD 等维度；用量、额度和账单自动读取需要相应 Google Cloud IAM 权限。
- Codex 产品存在 5 小时和每周使用窗口，但“产品内可查看”不等于“对第三方公开稳定 API”，必须在 M0 单独验证安全接入方式。
